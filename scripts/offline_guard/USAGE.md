# Проверка Python без внешней сети

Это **тестовый инструмент**, выключенный по умолчанию. Он не меняет Windows
Firewall, сетевые адаптеры, настройки браузера или другие процессы компьютера.
Модели и зависимости нужно скачать заранее.

## Быстрая проверка запрета

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe scripts/check_offline_guard.py --log-dir data/offline-guard-probe
```

Успех означает, что тестовые TCP, DNS и UDP обращения были отклонены до передачи,
соединение с `127.0.0.1` прошло, а новый дочерний Python загрузил тот же guard.
Адреса внешних проб — зарезервированные `192.0.2.1` и `offline-probe.invalid`;
пробы не отправляют запись или её текст. При отключении защиты проверка завершается
ошибкой, а не выдаёт положительный результат.

## Запуск приложения или E2E

Python-сценарии в `scripts/` могут использовать готовый контракт:

```python
from check_offline_guard import guard_environment

env = guard_environment(run_dir / "network", base=existing_environment)
process = subprocess.Popen(
    [sys.executable, "-m", "autoprotocol.launch"],
    env=env,
)
```

Функция добавляет каталог `scripts/offline_guard` в начало `PYTHONPATH`, сохраняя
предыдущее значение, и устанавливает:

| Переменная | Значение |
| --- | --- |
| `AUTOPROTOCOL_OFFLINE_GUARD` | `1` |
| `AUTOPROTOCOL_OFFLINE_GUARD_LOG_DIR` | Абсолютный каталог агрегированных журналов |
| `HF_HUB_OFFLINE` | `1` |
| `HF_HUB_DISABLE_TELEMETRY` | `1` |
| `TRANSFORMERS_OFFLINE` | `1` |

Обычные Python-потомки `autoprotocol.launch`, worker и ML-этапов наследуют эти
переменные. Для независимого прогона также задайте отдельный `AUTOPROTOCOL_DATA_DIR`
и свободный `AUTOPROTOCOL_PORT`: guard сам не меняет базу данных или порт.

Каждый загруженный guard создаёт `python-<PID>.json`. В нём только версия guard,
PID/PPID, граница проверки и счётчики вида `socket.connect.allowed` или
`socket.getaddrinfo.blocked`. Нет адресов, командных строк, токенов, аудио или текста
транскрипта. Снимок атомарно обновляется после каждого учтённого сетевого события,
поэтому его можно читать и после принудительной остановки worker. В Windows
между Python-процессами иногда есть процесс перенаправления venv: PPID может
указывать на него, поэтому отсутствие прямой связи двух JSON по PPID не означает
отсутствия наследования.

После остановки дочерних процессов вызовите
`summarize_guard_logs(run_dir / "network")` из того же `check_offline_guard`.
Функция возвращает `active`, `guard_versions`, `pids`, `process_count`,
`counters`, `invalid_log_count` и `reasons`. Счётчики складываются только для
известных сетевых событий; произвольные строки из файлов не попадают в сводку.
Отсутствие журналов, повреждённый JSON, неизвестная версия, несовпадение PID с
именем файла или неактивная запись дают `active: false` и явную причину.
CLI-проверка включает эту сводку в свой JSON и завершится ошибкой при
`active: false`.

Используйте отдельный каталог для каждого прогона: сводка читает все
`python-*.json` внутри него. `active: true` подтверждает только процессы,
представленные валидными журналами; ожидаемые процессы без журнала необходимо
сверить отдельно. Этот признак не доказывает, что произвольный дочерний процесс
или нативная программа были охвачены guard.

Если guard явно включён, но каталог журнала не задан или недоступен, Python
завершается с кодом `78` до запуска приложения. Ошибка записи журнала во время
сетевой операции также прерывает эту операцию.

## Что проверяет версия 2

- Числовые IPv4/IPv6 loopback-адреса разрешены. Имена, включая `localhost`,
  внешние IP, wildcard-адреса и обратные DNS-запросы запрещены.
- Перехватываются стандартные Python socket API: connect/connect_ex, bind,
  sendto/sendmsg, прямой и обратный DNS; audit hook служит дополнительной проверкой.
- На Windows перехватываются также стандартные `asyncio.IocpProactor.connect`
  и `sendto`, вызывающие `ConnectEx`/`WSASendTo` напрямую.
- Отдельные тесты проверяют наследование, TCP/UDP/DNS, асинхронные обращения,
  сохранение локальных соединений и отсутствие содержимого записи в журналах.

Предварительная проверка Python socket методов нужна потому, что CPython
разрешает имя адреса **до** события `socket.connect`; одного audit hook
недостаточно для предотвращения DNS. Это видно в
[исходном коде CPython 3.11](https://github.com/python/cpython/blob/v3.11.13/Modules/socketmodule.c#L3094-L3139).

## Границы результата

Это не изоляция на уровне ОС и не защита от враждебного Python-кода. Guard не
контролирует отдельные нативные процессы `ffmpeg`/`llama-server`, нативные расширения,
которые напрямую вызывают системные сетевые API, уже открытые внешние дескрипторы,
Python с `-I`/`-E`/`-S` или изменённым окружением. Такие случаи нельзя считать
проверенными на основании Python-журналов. Отсутствие замеченных соединений при
периодическом наблюдении за нативными процессами тоже не доказывает запрет сети.

Поэтому успешный прогон следует описывать как «E2E с блокировкой стандартных
Python сетевых API», указывая версии guard из журналов. Для утверждения «проект
работает при физически отключённой внешней сети / изоляции ОС» нужен отдельный
прогон в соответствующей среде.
