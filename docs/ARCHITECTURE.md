# Архитектура и границы реализации

## Размещение

```text
Браузер (localhost)
  └─ FastAPI + Jinja2 + static
       ├─ SQLite: встречи, задания, результаты, ручные версии
       └─ data/: оригиналы, нормализованное аудио, экспорт
              ↑
       отдельный Python worker
         FFmpeg → STT → диаризация → объединение
         после ручного сохранения: отдельное задание Qwen3 → JSON → проверка цитат
              ↑
       models/: локальные веса; без автоскачивания при обработке
```

Работают web-процесс, SQLite meetings/jobs, worker, локальные STT/диаризация
и объединение транскрипта, редактор имён/реплик с историей, локальные черновые
поручения, саммари, показатели и проблемы. DOCX формируется из согласованного
снимка сохранённых версий по двум шаблонам; файл отдаётся из памяти без записи на сервере.
[Актуальные контракты и ограничения](PHASE_2_REPORT.md).

## Структура

- `src/autoprotocol/main.py` — factory, HTTP-загрузка, встречи, результат, аудио и health.
- `config.py` — типизированная конфигурация из окружения/.env.
- `storage.py` — SQLite bootstrap, транзакции, WAL и foreign keys.
- `review.py` — ручные правки, подтверждённые имена, история и контроль версий.
- `analysis.py` — очередь анализа и снимок версии; `pipeline/extract.py` — LLM и проверка источников.
- `analysis_review.py` — правки поручений, саммари и докладов с отдельной историей.
- `export_docx.py`, `templates/` — снимок данных и экспорт с сохранением оформления образцов.
- `diagnostics.py` — проверка окружения без внешних запросов.
- `jobs.py` — очередь и lease; `worker.py` — отдельная обработка этапов.
- `launch.py` — совместный запуск и остановка web + worker; `media.py` — ffprobe.
- `web/` — локальные шаблоны и статика.
- `pipeline/` — STT, диаризация и объединение результатов.
- `tests/` — проверки инфраструктуры; `scripts/` — установка и запуск Windows.
- `data/`, `models/` — локальные данные, исключённые из git.
- `docs/` — решения, фазы, модельные зависимости.

## Контракты API

| Метод и путь | Назначение |
|---|---|
| POST /api/meetings | Байты файла application/octet-stream; метаданные в query; ответ 202 + id |
| GET /api/meetings | Последние 100 встреч |
| GET /api/meetings/{id} | Статус queued/processing/ready/failed, stage, безопасная ошибка |
| GET /api/meetings/{id}/result | Текущая ручная версия; `?original=true` возвращает исходный JSON |
| PATCH /api/meetings/{id}/result | Правки с expected_revision и source_digest; конфликт — 409 |
| GET /api/meetings/{id}/revisions | Последние 100 сохранений с old/new и временем |
| POST /api/meetings/{id}/analysis | Очередь анализа с expected_revision/source_digest |
| GET /api/meetings/{id}/analysis | Последний анализ, статус, stale и сохранённый результат |
| GET /api/meetings/{id}/audio | Аудио с Range для проигрывания источников |
| POST /api/meetings/{id}/export.docx | DOCX по template 1/2; версии, организация, темы и должности в JSON |

Также доступны `/`, `/static/*`, `/openapi.json`, `/health/live` (200),
`/health/ready` (503 до приёмки качества RU/KK/mixed и полного offline-сценария).
Liveness означает только готовность web-сервера.

## Данные и очередь (фаза 2)

Meeting хранит дату nullable, IANA timezone, status и stage; сегменты пока хранятся в JSON.
Миграция v3 добавляет review_states (снимок исходного JSON, SHA-256 и номер версии),
participants (подтверждённые вручную имена голосов), segment_edits и revisions.
Сущности привязаны к встрече и конкретному результату модели; исходные слова,
таймкоды и флаги остаются в JSON. Подробнее — [ручная проверка](MANUAL_REVIEW.md).
Миграция v4 добавляет analyses: неизменный снимок входа, версия, статус,
lease/owner/attempt, проверенный JSON поручений/саммари. Старые результаты не
прикладываются к новой версии как актуальные. Подробнее — [фаза 4](PHASE_4_REPORT.md).
Миграция v5 добавляет analysis_reviews (analysis_id, revision, JSON редактируемых
полей) и analysis_revisions (время и история old/new). JSON модели в analyses
остаётся неизменным. GET analysis накладывает правки и возвращает original,
manual_fields, reviewed, excluded и result.review.revision; ?original=true
возвращает исходный JSON. Evidence берётся только из проверенного вывода модели.
PATCH /api/meetings/{id}/analysis/{analysis_id}/review сохраняет правки атомарно
при совпадении версии и актуальном транскрипте. GET того же пути с /revisions
вместо /review отдаёт историю, в том числе для старого analysis_id.
Экспорт фиксирует обе версии, analysis_id и digest в одной read-транзакции;
при несовпадении возвращает 409. excluded убирает пункт из таблиц и саммари,
reviewed/manual_fields отражаются в документе; полный транскрипт сохраняется.
Миграция v6 добавляет prompt_version в analyses и ключ дедупликации: новый промпт
может обработать прежний транскрипт, сохранив старый результат и историю правок.
Старые результаты отмечаются upgrade_available. reports содержит направление,
показатель, проблему и evidence; показатель и проблема проверяются как точные
подстроки источников. Наличие цитат не гарантирует семантическую правильность.

Job содержит meeting_id, attempt, owner, lease_until и heartbeat; stage хранится в Meeting. Захват через
короткую транзакцию BEGIN IMMEDIATE; inference идёт вне транзакции. Один worker,
одна модель в памяти за раз. Упавший процесс освобождается по истечении lease;
повторы ограничены, результаты этапов записываются атомарно и идемпотентно.
Неизвестный процент заменяется названием этапа, а не фиктивным progress bar.

## Контур и эксплуатация

По умолчанию слушаем только 127.0.0.1. Авторизации и безопасного общего доступа
в каркасе нет; многопользовательское развёртывание — отдельная задача.
Браузер не использует CDN, внешние шрифты и аналитику. ML не принимает endpoint
от пользователя. Основной профиль предполагает локальный llama.cpp с loopback;
иной контролируемый адрес допускается только конфигурацией администратора.
Сетевые ограничения должны подтверждаться offline-тестом, env-флаги сами по себе
не являются сетевой изоляцией. В логах только id, этап, длительность и тип ошибки.

Резервное копирование SQLite выполнять через backup API при согласованном снимке
файлов; не копировать только основной файл при активном WAL. Удаление встречи
должно удалять связанные записи и медиа по явному действию пользователя.
Контейнеризацию/GPU-профиль добавлять после подтверждения зависимостей и моделей.
