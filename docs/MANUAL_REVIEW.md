# Ручная проверка транскрипта, поручений и итогов

Реализована часть фазы 5: имена голосов, исправление текста и говорящего,
отметки проверки, сохранение и история. Поручения и саммари доступны
отдельным [локальным анализом](PHASE_4_REPORT.md) и редактируются после его
завершения; доступен [DOCX по двум шаблонам](PHASE_6_REPORT.md). [Проверки редактора](PHASE_5_REPORT.md).
Дополнительные модели и зависимости для редактора не требуются.

## Сценарий

После обработки откройте встречу. Введите известное имя рядом с меткой голоса и
подтвердите соответствие. Прослушайте реплики по таймкодам, исправьте текст/голос,
отметьте проверенные реплики и нажмите «Сохранить изменения». После обновления
страницы должны сохраниться имена, текст, говорящие и отметки проверки.
В каждой реплике доступно исходное распознавание; под списком — история.

Имя можно снять очисткой поля и подтверждения. Редактирование текста/голоса снимает
галочку проверки в UI. Неизвестный говорящий допустим; выбор ограничен голосами
данной записи, в том числе кандидатами в неоднозначных словах. Создания нового
голоса, автоматического распознавания имён и объединения нескольких голосов нет.

## API

`GET /api/meetings/{id}/result` возвращает исходную структуру с дополнениями:

- `participants`: speaker_id, display_name (nullable), confirmed, mapping_source;
- `segments`: актуальные text/speaker_id, original, reviewed, manual_fields;
- `review`: revision, source_digest, счётчики проверки и previous_source_reviews.

`words`, `review_flags`, `source_segments` и `statistics` относятся к исходным моделям.
После правки текста таймкоды отдельных слов не пересчитываются;
`word_alignment_source="model"` явно обозначает это. Счётчик спорных непроверенных
реплик находится в `review.unreviewed_flagged_segments`.
`speaker_names_confirmed` означает, что имена всех обнаруженных голосов указаны
вручную; он не доказывает точность диаризации или проверку всех реплик.

`GET /api/meetings/{id}/result?original=true` возвращает JSON модели без ручных правок.

`PATCH /api/meetings/{id}/result` принимает частичный список объектов,
но каждый включённый объект передаётся целиком:

```json
{
  "source_digest": "<64 hex-символа из GET result>",
  "expected_revision": 0,
  "participants": [
    {"speaker_id": "SPEAKER_00", "display_name": "Алия", "confirmed": true}
  ],
  "segments": [
    {"id": "aligned_0001", "text": "Уточнённая реплика.", "speaker_id": "SPEAKER_00", "reviewed": true}
  ]
}
```

Значения в примере условные: используйте существующие идентификаторы и digest
конкретной встречи. Один PATCH сохраняет все изменения атомарно и возвращает
актуальный результат. Номер версии растёт только при фактических изменениях.
Имя требует `confirmed=true`; снятие имени — `display_name=null, confirmed=false`.
Лишние поля, дубликаты идентификаторов, пустой текст, чужие сегменты и голоса — 422.
Несуществующая встреча — 404; неготовый результат или конфликт версии/digest — 409.
Origin проверяется аналогично загрузке. Авторизации пользователя пока нет.

`GET /api/meetings/{id}/revisions` возвращает последние 100 сохранений, новые первыми:
номер, digest результата, серверное время UTC, `change_source="manual"`, список
entity/id/field/old/new. Имя автора не заявляется: аккаунтов в локальной версии нет.

## Хранение и конкуренция

Миграция v3 сохраняет прежние встречи и очередь, добавляя:

| Таблица | Данные |
|---|---|
| review_states | meeting_id + SHA-256 исходного файла, снимок JSON, revision |
| participants | Подтверждённое вручную имя для speaker_id в конкретном результате |
| segment_edits | Текущие исправления текста, голоса и отметки проверки |
| revisions | Неизменяемая история полей: прежнее/новое значение и время |

Сохранение выполняется в `BEGIN IMMEDIATE`: версия проверяется и меняется в одной
транзакции. Два конкурентных PATCH с одинаковым expected_revision не могут
молча затереть друг друга. Чужой идентификатор отклоняет весь запрос без частичной записи.
При 409 браузер оставляет черновик в полях. Перед загрузкой актуальной версии
пользователь копирует нужные изменения; автоматического слияния нет.

Исходный файл модели не изменяется. Правки привязаны к meeting_id и SHA-256
конкретного результата, поскольку aligned_0001 в новом inference может обозначать
другую реплику. При замене результата старые правки и снимок остаются в БД/истории,
но не накладываются на новый текст; UI показывает предупреждение. Если байты
результата те же, прежние правки продолжают применяться. Кнопки повторной обработки
пока нет; это защита хранения для будущего этапа, а не новая функция интерфейса.

Извлечение поручений использует снимок сохранённой ручной версии и фиксирует
revision/source_digest; устаревший анализ помечается в интерфейсе. Экспорт
фиксирует эти значения и версию правок анализа, отклоняя конфликт с кодом 409.

## Проверки и ограничения

- На этапе редактора прошли 53 pytest-теста, включая 14 тестовых случаев редактора;
  актуальное число с фазой 4 указано в README.
- Сохранение/чтение после перезапуска приложения, сохранность исходного файла и слов.
- Реальные конкурентные записи SQLite: одна проходит, другая получает 409.
- История, снятие имени, возврат исходного текста, отсутствие версий для no-op.
- Атомарный отказ при ошибках, изоляция одинаковых записей разных встреч.
- Миграция v2 → v3 без потери готовых встреч/заданий, повторная инициализация.
- Новое распознавание не получает правки старых сегментов; старый снимок сохранён.
- Ruff, форматирование и синтаксис JavaScript.
- В Chrome открылась отдельная синтетическая встреча редактора (без ML), ввод
  имени и текста отразился в форме. Браузерное сохранение, перезагрузка и визуальный
  вид тогда не были приняты: инструмент остановился, не сумев надёжно определить текущий URL;
  получение снимка окна также оказалось недоступно. Backend-проверки выполнены отдельно.

Синтетический тест интерфейса не является новым измерением STT/диаризации.
Реальные записи и новые тяжёлые ML-прогоны для изменения редактора не использовались.

## Поручения и итоги: редактор v5

Редактируются task, assignee_text, due_text, due_kind, status у поручений и
text/kind у итогов. reviewed подтверждает проверку человеком; excluded исключает
пункт из будущего протокола без удаления. Изменение поля в интерфейсе снимает
галочку проверки. Исходные цитаты и их времена неизменны; ручной текст может
отличаться от цитаты и явно отделён от исходного ответа модели.

`GET /api/meetings/{id}/analysis` теперь возвращает наложенные правки в result:
у пунктов есть id, original, manual_fields, reviewed, excluded и requires_review;
версия правок — result.review.revision. `?original=true` возвращает исходный вывод.

`PATCH /api/meetings/{id}/analysis/{analysis_id}/review` принимает
expected_revision, actions, summary и reports. Списки могут быть частичными, но каждый
включённый пункт передаётся со всеми редактируемыми полями, id, reviewed и excluded.
Идентификаторы берутся из GET; добавление новых пунктов не поддерживается.
Пустой ответственный преобразуется в null. Пустому сроку должны соответствовать
due_text=null и due_kind=unspecified. Календарные поля пересчитываются по сохранённой
дате встречи; ввод произвольной нормализованной даты через API запрещён.

Сохранение использует BEGIN IMMEDIATE и отдельную версию поручений. Устаревший
транскрипт, неготовый анализ или конфликт версии дают 409; чужой analysis_id — 404;
неизвестный пункт, лишние поля, дубликаты и неверная структура — 422.
Запрос не перезаписывает result_json и не меняет evidence. Повторное сохранение
тех же значений не увеличивает версию.

`GET /api/meetings/{id}/analysis/{analysis_id}/revisions` возвращает последние
100 сохранений: revision, changed_at, change_source=manual и changes с id/field/old/new.
История старого анализа сохраняется после нового запуска; автоматического переноса
правок между анализами нет. В UI показывается история выбранного текущего анализа;
история прежнего доступна по его analysis_id через API.

Пока есть несохранённые поручения, редактор транскрипта и запуск анализа недоступны.
Фоновый опрос не заменяет черновик. При конфликте нужно скопировать нужный текст
перед нажатием «Загрузить сохранённые поручения». После правки транскрипта прежние
поручения доступны только для чтения; требуется новый анализ.

## Показатели, проблемы и экспорт

Новый анализ автоматически извлекает reports: direction, indicator, problem и
evidence. Последние два поля nullable: отсутствие данных не заменяется нулём.
Автоматические значения должны дословно встречаться в цитатах; человек может
исправить формулировки с сохранением original/manual_fields и истории.
Поля, reviewed и excluded сохраняются той же кнопкой, что поручения и саммари.

Для старого промпта интерфейс предлагает новый анализ без повторного STT.
Миграция v6 сохраняет прежние analysis_id и правки; новый анализ создаётся отдельно.
История прежнего анализа остаётся доступна через API, но не переносится автоматически.
До обновления шаблон №2 недоступен, поскольку у старого результата нет reports.

В DOCX включаются только сохранённые поля. Источники, таймкоды и версии вынесены
в приложение; исключённые пункты не попадают в саммари и таблицы. Организация,
должности и тематические границы задаются вручную для текущего скачивания;
они не сохраняются как новые поля встречи и не являются результатом модели.
